# 02 · 구현 설계서

> `01-기획서.md`의 규칙을 코드로 옮기는 방법. 코드 예시는 TypeScript 기준이지만 3장의 선택에 따라 바뀔 수 있다.

---

## 1. 전체 구조

```
┌────────────── 사용자의 프로젝트 (Claude Code 실행) ──────────────┐
│  .claude/settings.json  훅 → curl POST (비동기, 1초 제한, 실패 무시) │
│  .claude/agents/*.md    팀원 정의                                  │
│  (마을 설정은 ~/.subagent-tycoon/settings/<id>.json — 프로젝트 밖) │
└───────────────┬──────────────────────────────────────────────────┘
                │ HTTP POST /hook  (127.0.0.1:4777)
┌───────────────▼──────────── 수집기 (collector) ───────────────────┐
│ 1. 받은 JSON을 그대로 raw_events에 추가 (append-only)               │
│ 2. 정규화 → domain_events (2장)                                     │
│ 3. 프로젝터가 상태를 갱신 (결정적 · 재생 가능)                          │
│ 4. 게임 시계: 일하는 동안만 시간이 흘러(활동 시간) 하루마다 정산·성격 │
└───────────────┬──────────────────────────────────────────────────┘
                │ REST (스냅샷) + SSE (변경분)
┌───────────────▼──────────── 웹 UI ────────────────────────────────┐
│ React + SVG. 마을 렌더러, 캐릭터 리그 런타임, 화면 6종               │
└──────────────────────────────────────────────────────────────────┘
```

핵심 원칙

1. **Claude Code를 절대 느리게 하거나 막지 않는다.** 훅은 비동기, 1초 제한, 실패해도 `|| true`. 수집기는 응답에 아무 판단(JSON 결정)도 넣지 않는다.
2. **원본 이벤트는 지우지 않는다.** 상태는 언제든 raw_events를 처음부터 재생해 다시 만들 수 있어야 한다 (규칙을 바꾸면 재생).
3. **시간과 난수는 주입한다.** 프로젝터는 `now()`와 `Math.random()`을 직접 부르지 않는다. 이벤트 시각과 seed 난수만 쓴다 → 테스트가 결정적.

## 2. 데이터 수집

### 2.1 훅

예시 설정: `examples/target-project/.claude/settings.json`. 모든 이벤트를 같은 `/hook` 주소로 보낸다.

**설치 도구** (2026-09-30 사용자 요청: 저장소를 받은 사람이 자기 프로젝트에 똑같이 쓰게) — `pnpm connect <프로젝트 경로>` (`tools/connect.ts`. `pnpm setup`은 pnpm 기본 명령이라 피함):
- **원칙 (사용자 결정): 사용자 프로젝트에는 관여하지 않는다.** 마을에 필요한 훅만 넣고, 에이전트·팀 공유 설정·git 설정 등 그 사람이 꾸린 것은 건드리지 않는다. 그 사람이 만든 에이전트(`.claude/agents`)는 수집기가 읽어 마을에 보여 주기만 한다. (처음엔 범용 팀 에이전트 6명을 복사하고 `.git/info/exclude`를 고쳤으나 사용자가 되돌림)
- 훅: 위 예시의 `hooks`를 대상 프로젝트 `.claude/settings.local.json`(나만 쓰는 파일, 팀에 공유되지 않음)에 합친다. 그 파일의 다른 설정은 그대로, 쓰기 전 `<파일>.tycoon.bak`(사용자가 만든 `.bak`을 덮지 않게), 임시 파일에 쓴 뒤 바꿔 끼움, 깨진 JSON이면 쓰지 않음. 같은 수집기 주소 훅이 `settings.json`·`settings.local.json` 어디든 이미 있는 이벤트는 건너뛴다(두 번 보내면 이벤트가 겹침) → 몇 번 돌려도 같다. `TYCOON_PORT`면 그 포트로. git에 올리지 않도록 안내만 한다.
- **전역 한 번** (2026-09-30 사용자 결정, 01 문서 D22): `pnpm connect --global`은 같은 합치기(`mergeHooks`·`.tycoon.bak`·임시 파일·깨진 JSON이면 안 씀)로 사용자 전역 `~/.claude/settings.json`에 훅을 넣는다(`.claude` 폴더가 없으면 만듦, 다른 설정·사용자가 가진 다른 훅은 그대로). Claude Code는 전역 훅을 모든 프로젝트에서 돌리고 수집기는 훅이 보내는 `cwd`로 마을을 나누므로, 어느 폴더에서 열든(홈·임시 폴더 포함) 그 폴더의 마을이 생긴다. 프로젝트 폴더엔 아무것도 안 생겨 "관여하지 않는다"에도 맞다. 프로젝트 모드는 전역 파일도 팀 공유 `settings.json`처럼 "이미 있는 곳"으로 보고 그 이벤트를 건너뛴다 — 전부 전역에 있으면 파일을 만들지 않고 알린다. 이미 프로젝트로 연결한 뒤 전역을 걸어도 로컬 훅은 지우지 않는다 — Claude Code는 같은 훅(명령·matcher가 같음)이 여러 설정 파일에 있으면 한 번만 돌린다 (공식 훅 문서 "If you define the same handler in more than one settings file, it runs once", 2026-09-30 확인). 되돌리기: `.tycoon.bak` 또는 `127.0.0.1:<port>/hook` 훅 지우기.

- 기본은 `type: "command"` + `curl`. 최근 버전에 `type: "http"` 훅이 있다면 그걸로 바꿔도 된다 (curl 프로세스가 안 떠서 가볍다).
- **구현 전에 반드시 확인할 것**: 설치된 Claude Code 버전의 훅 문서(https://code.claude.com/docs/en/hooks)에서 ① 이벤트 이름 목록 ② 서브에이전트 식별 필드(`agent_id`, `agent_type`) ③ 위임 도구 이름(`Agent`, 예전 이름 `Task`) ④ 작업 도구(`TaskCreate`/`TaskUpdate`, 예전 `TodoWrite`) ⑤ `http` 훅 형식. 이 설계서를 쓸 때 조사한 값이지만 버전마다 다를 수 있다.
- 지원하지 않는 이벤트 이름이 설정에 있으면 경고가 날 수 있으니 버전에 맞게 지운다.

사용하는 이벤트

| 훅 이벤트 | 쓰는 필드 | 용도 |
|---|---|---|
| SessionStart / SessionEnd | session_id, cwd, source | 마을 선택, 세션 경계 |
| UserPromptSubmit | prompt (앞 20자만 저장) | 회의 |
| PreToolUse / PostToolUse / PostToolUseFailure | tool_name, tool_input, tool_response(요약), agent_id, agent_type | 작업 생성·갱신, 위임, 도구 통계, 테스트 판별 |
| SubagentStart / SubagentStop | agent_id, agent_type, (마지막 메시지) | 팀원 작업 시작·끝(끝날 때 급여), 성격 T/F |
| Notification | notification_type / message | 막힘 (권한 요청), `idle_prompt`(입력 기다림) = 메인 턴 끝 |
| Stop | — | 메인 턴 끝 → 회의 해산 판단, 활동 시간 (01 문서 6.2) |
| StopFailure | — | API 오류로 끝난 메인 턴 (`Stop` 대신 옴). 2.1.278에서 확인 |

### 2.2 대체 수집 (훅이 부족할 때)

- 트랜스크립트 꼬리 읽기: `~/.claude/projects/<slug>/<session>.jsonl`, 서브에이전트는 `<session>/subagents/<agent-id>.jsonl` (버전에 따라 다름). 훅에 없는 필드(최종 메시지 등)를 보충할 때만 쓴다.
- 이 방식은 선택 기능. 기본은 훅만.

### 2.3 개인 정보

- 수집기는 `127.0.0.1`에만 바인딩한다. `Host`가 루프백 이름(`127.0.0.1`·`localhost`·`[::1]`)이 아니거나 `Origin`이 있는데 루프백이 아니면 403 (DNS 리바인딩, 다른 사이트의 `/hook` 위조 차단).
- `tool_input`, `tool_response`는 원문을 저장하지 않는다. 도구 이름, 파일 경로의 확장자, 명령의 첫 단어, 성공 여부, 글자 수만 남긴다. 예외: 작업 제목(`subject`), 서브에이전트 최종 메시지(성격 계산용, 설정으로 끌 수 있음).
- **토큰 사용량** (D11, 01 문서 6.2): 훅 본문에는 토큰 수가 없다(2026-09-30 훅 문서 확인). 수집기가 `SubagentStop`·`Stop`을 받을 때 Claude Code 기록 파일에서 응답마다의 `message.usage` **숫자 4개만**(`input_tokens`·`output_tokens`·`cache_creation_input_tokens`·`cache_read_input_tokens`) 합쳐 요약본 `tokens`로 남긴다. 대화 내용은 읽어도 저장하지 않는다.
  - 서브에이전트: `<transcript_path에서 .jsonl을 뺀 폴더>/subagents/agent-<agent_id>.jsonl` (훅이 `agent_transcript_path`를 주면 그것). `SubagentStop`마다 처음부터 읽어(읽은 위치를 버림) 그 파일의 **누적** 합이다 — 이어 받은 서브에이전트(같은 `agent_id`, 5.2)는 구간을 넘어 쌓이므로 프로젝터가 앞 구간 끝 누적(`AgentRun.cum`)과의 차이만 청구한다. 팀장: `transcript_path`에서 `isSidechain`이 아닌 응답의 **누적** 합 — 프로젝터가 세션마다 앞 누적과의 차이만 청구한다.
  - 한 응답이 내용 블록마다 여러 줄로 쪼개져 같은 `usage`가 되풀이된다 → `message.id`로 한 번씩만 센다 (실측: 65줄 = 응답 38개).
  - **모델·1시간 캐시·빠른 모드** (D13, 01 문서 6.7): `cacheWrite`는 5분 캐시 쓰기만, `cacheWrite1h` = `usage.cache_creation.ephemeral_1h_input_tokens`. 요약본 `usage.models`에 모델별(`message.model`, 빠른 모드면 뒤에 ` fast`) 합.
  - **영수증 재료** (D13): 요약본 `usage = { calls, first, last, models, parts }` — 호출 수, 첫·마지막 호출 맥락 크기, 모델별 사용량, 원인별(`base`·`rebuild`·`tool:<도구 이름>`) 토큰 수. 도구 결과는 **글자 수만** 세고(`tool_use_id`로 도구 이름을 찾음) 내용은 버린다. 계산은 01 문서 6.7-2. 팀장은 세션 누적.
  - 이 파일 형식은 "내부용, 버전마다 바뀜"(공식 문서)이라 못 읽으면 `tokens`를 비운다(비용 없음). `.jsonl`만, 한 번에 새로 붙은 줄만 읽는다(파일마다 읽은 위치를 기억, 수집기를 다시 켜면 처음부터 한 번).
- raw_events에는 위 요약본을 저장한다. "원문 보관"은 설정으로만 켠다. 최종 메시지는 `collector.keepLastMessage: false`(tycoon.json `overrides`)로 끈다.
- 최종 메시지(`AgentRun.lastMessage`)는 수집기 안에서 성격 계산에만 쓴다. `/state`·SSE·`/replay` 스냅샷에서는 뺀다 (M8 리뷰 — 화면은 안 쓰고, 실행마다 최대 2000자라 스냅샷만 커졌음).

## 3. 기술 스택 선택지

### 3.1 백엔드 · 저장소

| 안 | 구성 | 장점 | 단점 |
|---|---|---|---|
| A | Node + TypeScript (Fastify) + SQLite (better-sqlite3) | 프론트와 언어·타입 공유, 설치 한 번, 가장 단순 | 분석 쿼리·집계는 직접 코드로 |
| B | Python (FastAPI) + DuckDB, 변환은 SQL 모델(raw → staging → marts) | 이벤트 파이프라인·SQL 변환을 제대로 연습, 경제·성격 지표를 SQL로 투명하게 | 프론트와 타입 이중 관리, 실시간 상태는 결국 코드로 따로 |
| C | A + 분석용 DuckDB를 옆에 (raw_events를 Parquet로 내보내 집계) | 실시간은 단순하게, 분석은 SQL로 | 구성 요소가 늘어남 |

**권장: A로 시작, 경제 패널(M7) 즈음 C를 검토.** 실시간 상태는 이벤트 하나마다 즉시 바뀌어야 해서 코드 안의 리듀서가 맞고, 기간별 집계(30일 기금 흐름, 주별 흐름)는 SQL이 편하다. 데이터 엔지니어링 연습이 목적이라면 처음부터 B나 C로 가도 되고, 그 경우 raw → staging → marts 계층과 테스트(행 수, null, 재생 일치)를 문서화하면 포트폴리오 설명거리가 된다.

### 3.3 실시간 전달

- **SSE 권장** (서버 → 브라우저 한 방향이면 충분, 재연결 내장). 상태 변경분(patch)을 보낸다.

## 5. 이벤트 모델

### 5.1 저장

```sql
CREATE TABLE raw_events (
  seq        INTEGER PRIMARY KEY AUTOINCREMENT,
  received_at TEXT NOT NULL,          -- 수집기 시각 (ISO)
  project    TEXT NOT NULL,           -- cwd 정규화
  session_id TEXT,
  hook       TEXT NOT NULL,           -- hook_event_name
  payload    TEXT NOT NULL            -- 요약된 JSON (2.3)
);
CREATE TABLE snapshots (               -- 재생 속도용 체크포인트
  project TEXT, seq INTEGER, state TEXT, PRIMARY KEY (project, seq)
);
```

M4 구현: `raw_events`에 `dedupe_key TEXT UNIQUE`(`project|session|tool_use_id 또는 시각|hook|agent_id`)를 더해 `INSERT OR IGNORE`로 중복을 버린다. 실제 훅 본문엔 시각이 없어 수집기가 받은 시각을 `_t`로 찍는데, 이 시각으로는 중복을 판단하지 않는다(키 NULL): 같은 ms의 다른 훅을 버리게 된다. `_t`가 본문에 있는 줄(픽스처·녹화)과 `tool_use_id`가 있는 줄만 중복을 본다. `pnpm replay file.jsonl`은 `_t` 없는 줄을 거부한다(재생이 결정적이지 않음). DB는 WAL(읽는 프로세스가 쓰기를 막지 않음). `snapshots`는 아직 만들지 않았다 (시작·재생이 느려지면). 수집기가 만드는 내부 줄은 `hook: 'roster'`(SessionStart 때, 또는 처음 보는 마을이면 첫 이벤트보다 먼저 `.claude/agents` + `tycoon.json` → `RosterLoaded`), `hook: 'clock'`(마을이 일하는 중일 때 `TYCOON_CLOCK_MS`마다 → `Tick`, 시간만 흐름. 2026-09-30 전의 옛 줄은 벽시계 날 `day`가 있지만 버리고 `Tick`으로 재생 — 01 문서 6.2 활동 시간), `hook: 'ui'`(사용자 행동. M6: `{ kind: 'rename', buildingId, name }` → `BuildingRenamed`, M7: `{ kind: 'purchase', memberId, furniture, fabric }` → `FurniturePurchased`(줄의 `kind`가 행동 이름이라 가구 종류는 `furniture` 필드), `{ kind: 'move', memberId, furnitureId, placed }` → `FurnitureMoved`. 중복 판단 안 함) 세 가지이고, `/hook`으로 들어온 같은 이름은 버린다.

### 5.2 정규화된 도메인 이벤트

```ts
type DomainEvent =
  | { t: 'SessionStarted'; at: number; project: string; sessionId: string }
  | { t: 'PromptSubmitted'; at: number; sessionId: string; preview: string }
  | { t: 'TaskCreated'; at: number; taskId: string; subject: string }
  | { t: 'TaskStatusChanged'; at: number; taskId: string; status: 'pending' | 'in_progress' | 'completed' | 'deleted' }
  | { t: 'AgentRunStarted'; at: number; runId: string; agentType: string; resumed?: boolean }  // agent_id, agent_type. resumed = 이어 받은 구간 (프로젝터가 붙임)
  | { t: 'AgentRunEnded'; at: number; runId: string; ok: boolean; lastMessage?: string }
  | { t: 'ToolUsed'; at: number; runId: string | null; tool: string; ok: boolean; kind: ToolKind; isTest: boolean;
      chars?: number; agentType?: string }               // 편집·쓰기 내용 글자 수(숫자만) — 성격 큰 편집 (01 문서 7장). agentType = 서브에이전트 도구의 agent_type
  | { t: 'PermissionPrompt'; at: number; runId: string | null }
  | { t: 'MainTurnEnded'; at: number; sessionId: string }
  | { t: 'Tick'; at: number }                                                   // 수집기 'clock' 줄: 시간만 흐름 (활동 시간)
  | { t: 'GameDayTick'; at: number; day: number }                               // 프로젝터 안에서만 만듦 (6.1). raw 줄 없음
  | { t: 'BuildingRenamed'; at: number; buildingId: string; name: string }      // 'ui' rename (M6)
  | { t: 'SessionEnded'; at: number; sessionId: string }                         // SessionEnd (M7): 열린 실행을 닫는다
  | { t: 'FurniturePurchased'; at: number; memberId: string; kind: string; fabric: string | null }   // 'ui' purchase (M7)
  | { t: 'FurnitureMoved'; at: number; memberId: string; furnitureId: string;
      placed: { x: number; y: number; rot: 0 | 1 } | null };                  // 'ui' move (M7), null = 창고. furnitureId = 구매에서 정한 고정 id (01 문서 6.4·D30: u<시각>, a<날>.<팀원>.<k>)

type ToolKind = 'read' | 'search' | 'edit' | 'write' | 'shell' | 'web' | 'plan' | 'other';
```

정규화 규칙

- `runId`: `agent_id`가 있으면 그것, 없으면 `null`(메인 세션). 서브에이전트 도구 호출은 `agent_type`도 `ToolUsed.agentType`으로 싣는다.
- **실행 = 구간** (2026-10-01, 01 문서 3장·6.1): 이어 받은 서브에이전트(`SendMessage`)는 같은 `agent_id`로 다시 시작한다. 프로젝터가 규칙보다 먼저 `segment()`(core `rules/runs.ts`)로 `agent_id` → 실행 id를 바꾼다: 마지막 구간이 끝났으면 `AgentRunStarted`나 `PreToolUse`가 새 구간 `<agent_id>#n`(n = 2, 3…, 결정적)을 연다 — 시작을 못 본 도구 호출은 `AgentRunStarted`(주인 = `agentType`, 없으면 앞 구간)를 먼저 넣는다. 끝·늦게 온 Post·권한 요청은 마지막 구간에, 열린 구간에 온 시작은 같은 구간(중복), 시작도 도구도 못 본 끝(다음 입력 제안 포크)은 그대로 둬 규칙이 버린다. 이어 받은 구간의 시작엔 `resumed: true` → `Agent` 호출 대체 작업(5.1-5)과 짝짓지 않는다. 끝의 `tokens`·`usage`는 앞 구간 누적과의 차이로 바꾼다.
- `agent_type`이 `Explore | Plan | general-purpose`면 외부인, 등록된 md 이름이면 팀원, 그 밖은 "알 수 없는 외부인"으로 인력사무소 소속 처리.
- `TaskCreate`의 id는 `tool_response`에서 꺼낸다. 없으면 `subject + 시각` 해시.
- 같은 이벤트가 두 번 오면(`Pre` + `Post`) 한 번만 반영하도록 `(session_id, tool_use_id|시각, hook)`으로 중복 제거.
- `Stop`·`StopFailure`·`Notification` `idle_prompt` → `MainTurnEnded` (사용자가 중단하면 `Stop`이 없고 약 1분 뒤 `idle_prompt`만 온다 — 메인 턴이 안 닫혀 활동 시간이 흐르지 않게, 01 문서 6.2).
- `agent_id`가 없는 `Notification`(권한 요청)은 가장 최근에 시작해 아직 끝나지 않은 실행에 붙인다. 실행 중인 게 없으면 메인 세션(팀장).
- 테스트 명령 판별 목록(`test`, `pytest`, `vitest`, `jest`, `go test`, `cargo test`, `npm run test`, `pnpm test`)은 설정 `collector.testCommands`로 바꿀 수 있다. 명령 자리에서만 본다 (01 문서 6.1).
- `PostToolUseFailure`인 `TaskCreate`/`TaskUpdate`는 버린다 (작업이 생기거나 바뀌지 않았다). `SessionStart`의 `source: compact`는 세션 경계가 아니다. `agent_id`·`agent_type`·작업 id·도구 이름이 `__proto__`·`constructor` 같은 프로토타입 키면 그 줄을 버린다 (M7: 'ui' 줄의 팀원 id·가구 id·가구 종류도).
- `SessionEnd` → `SessionEnded` (M7). 규칙은 `SessionStarted`와 같이 열린 실행을 `ok = null`로 닫는다 (01 문서 4장).

  description: string; fromMd: boolean;     // md 설명(직업 키워드), 프로젝트 .claude/agents 팀원인가 (01 문서 3.1, D9)
  movedInAt: number | null;                 // 처음 일한 시각 = 입주(집). null = 입주 전 (마을에 없음). 시작 잔고는 없다 (D20)
  species: 'bear'|'rabbit'|'raccoon'|'penguin'|string; accessory: string | null;
  isLeader: boolean; departed: boolean;

  currentRunId: string | null; currentTaskId: string | null;

  hardship: boolean;                        // 토큰 비용을 다 못 내 0에서 멈춤 ("형편이 어려움"). 팀장은 늘 false
  tokens: number; tokenCostToday: number;   // 쓴 비용 환산 토큰 누적, 오늘 낸 토큰 비용 (D11)
  materialsToday: number;                   // 오늘 낸 일터 자재비 (06 문서 5.3), 정산 때 0 — 집 지갑 "자재비 · 오늘"

  personality: { EI: number; SN: number; TF: number; JP: number; letters: string;   // 점수 0~100, 글자는 히스테리시스 뒤
    drifting: { axis: Axis; toward: string; percent: number } | null;              // "T가 F 쪽으로 38%"
    reason: string; driftToday: Record<Axis, number>;                              // 하루 이동 한도
    samples: { taskId; at; EI; SN; TF; JP: number | null }[];                      // 최근 window개 작업, 숫자만
    lastMeetingAt: number | null };                                                // E/I 불참 판단 (M8, 01 문서 7장)
}

  createdAt: number; startedAt?: number; completedAt?: number;
  contributions: Record<string, number>;    // memberId|visitorKind → ms
  quality: 'testsPassed'|'noTests'|'failed'; toolCalls: number;
  salaryPaid: number;                       // 짝지어진 실행(AgentRun.taskId)이 받은 급여(세전) 합. 보여 주기용 — 급여는 실행마다 (D20)

interface AgentRun {   // (일부) 전체는 core `projector/types.ts`
  runId: string; agentType: string;
  memberId: string | null; visitorKind: string | null;   // 팀원이면 id, 외부인이면 종류
  startedAt: number; endedAt: number | null; lastAt: number;
  ok: boolean | null; toolCalls: number; testsPassed: number; testsFailed: number;
  tokens?: number;                          // 비용 환산 토큰 (끝날 때 한 번 청구, D11)
  wage?: number;                            // 급여(세전). 팀원 실행이 끝날 때 한 번 (D20, 01 문서 6.1). 있으면 이미 준 것. 외부인은 없음
  taskId?: string;                          // Agent 호출 대체 작업과 짝지어졌으면 그 작업
  cum?: { tokens: Tokens; usage?: Usage };  // 이 구간 끝에서 읽은 기록 파일 누적 (이어 받은 다음 구간은 차이만, 5.2). /state·SSE 스냅샷에선 뺀다

interface EconomyState {
  fund: number;                             // 마을 기금 = 팀장(시장)의 지갑 (D21): 세금 − 팀장 토큰값 − 팀장 가구 − 레벨업·공공시설
  deficit: boolean;                         // 시청 적자: 오늘이나 지난 정산 날에 기금이 팀장 토큰값을 다 못 낸 몫이 있음 (0에서 멈춤, 빚 없음). 못 낸 몫이 없는 날이 정산되면 꺼짐 (06 문서 3.3)
  today: { wages: number; tax: number; purchases: number; tokens: number;
    leaderTokens: number; leaderUnpaid: number; leaderPurchases: number; materials: number; works: number };   // 오늘 누적 (정산 때 비움). leaderUnpaid = 기금이 모자라 못 낸 팀장 토큰값 (돈이 아니라 기록), leaderPurchases = 기금에서 낸 팀장 가구 (purchases는 팀원 잔고에서 낸 가구만)
  history: DayRecord[];                     // 게임 하루마다 한 줄 (수집기는 최근 60일만 상태에 둔다)

interface DayRecord {
  day: number; at: number;
  wages: number; tax: number; purchases: number; tokens: number;   // 그날 급여 합(세전) · 세금 · 가구 지출 · 팀원이 낸 토큰 비용
  leaderTokens: number; leaderUnpaid: number;                      // 그날 기금에서 낸·못 낸 팀장 토큰값
  leaderPurchases: number;                                         // 그날 기금에서 낸 팀장 가구 (purchases = 팀원 가구만)
  materials: number;                                               // 그날 팀원이 낸 일터 자재비 (06 문서 5.3) — 팀원 잔고 = 급여 − 세금 − 가구 − 토큰 − 자재비
  works: number;                                                   // 그날 기금에서 낸 레벨업 공사비 + 공공시설 (06 문서 6.4) — 기금 = 세금 − 팀장 토큰값 − 팀장 가구 − works
  fund: number; balances: Record<string, number>;                  // 정산 뒤 기금, 팀원 잔고
}

  day: number; cost: number;                // 지은 게임 날, 기금에서 낸 값 (두 번째 랜드마크는 0 — 마지막 레벨업 공사비에 들어 있음)

interface Building {   // 팀원 일터 (06 문서 5장, D18·D19). 층·점수·낸 자재비는 내려가지 않는다
  id: string;                               // `w<n>:<memberId>` — 재생해도 같아 사용자 이름이 따라간다 (5.9)
  memberId: string; n: number;              // 주인(처음부터), 그 팀원의 몇 번째 일터

  waiting: 'materials' | 'level' | null;    // 게이지는 찼는데 모자란 것 (06 문서 5.4)
  startedAt: number; floorAt: number | null; // 부지를 잡은 시각, 마지막 층 오른 시각 (반짝임·거품)
}

- 순수 함수. 부수효과는 반환된 상태에 담긴 `toasts`/`feed`뿐.
- 규칙별 파일로 나눈다: `rules/tasks.ts`(작업·기여), `rules/workplace.ts`(일터: 부지·1층·일 점수·층 올리기 — 실행 시작, `finishRun` 뒤, 하루 정산 세 곳에 붙는다, 06 문서 5.9), `rules/economy.ts`, `rules/personality.ts`, `rules/meeting.ts`, `rules/status.ts`.
- 게임 하루 정산은 `GameDayTick` 이벤트로만 일어난다. **2026-09-30부터 `GameDayTick`은 프로젝터가 안에서 만든다** (raw 줄 없음): 이벤트마다 먼저 활동 시간(`clock.activeMs`, 01 문서 6.2)을 더하고, 하루 길이가 바뀌었으면 오늘 지난 몫을 새 하루 한 번까지로 자른 뒤(`dayStartMs = max(dayStartMs, activeMs − 새 길이)`), `passed = floor((activeMs − dayStartMs) / dayMs)`가 1 이상이면 `dayStartMs += passed × dayMs` 하고 `{ t: 'GameDayTick', at: e.at, day: day + passed }`를 규칙에 한 번 돌린 뒤 그 이벤트를 돌린다 (길이가 안 바뀌면 `floor(activeMs / gameDayMs)`와 같음). 밖에서 넣은 `GameDayTick`(규칙 테스트)은 그 순간을 새 날의 시작으로 본다. 활동 시간은 이벤트 시각과 상태만으로 정해지므로 재생해도 같은 결과. 수집기의 `'clock'` 줄(`Tick`)은 시간만 흘려 긴 실행 중에도 날이 제때 넘어가게 할 뿐 날을 정하지 않는다. 규칙 단위 테스트는 `GameDayTick`을 직접 넣어 날을 넘길 수 있다 (`clock.day`는 내려가지 않음).
- `activeUntil(state, cfg)` = 일하는 동안 시간이 흐를 수 있는 마지막 시각: 메인 턴이면 `clock.lastEventAt`, 끝나지 않은 실행마다 `AgentRun.lastAt`(시작 + 그 `runId`를 단 이벤트) 중 가장 늦은 것 + `activeGapCapMs` (01 문서 6.2). 프로젝터(`activeMs`)와 수집기(시계 줄을 넣을지)가 같이 쓴다. 상한을 일마다 재는 까닭: 버려진 실행 하나가 다른 턴의 이벤트로 계속 일하는 중으로 보이지 않게 (리뷰 2026-09-30).

## 7. 렌더링

### 7.1 좌표

```ts
const TILE_W = 64, TILE_H = 32;
function iso(x: number, y: number) { return { sx: (x - y) * TILE_W / 2, sy: (x + y) * TILE_H / 2 }; }
// 에셋 배치: 화면 위치 = iso(중심) − data-anchor
// 1×1 중심 = (x+0.5, y+0.5), 2×1 = (x+1, y+0.5), 2×2 = (x+1, y+1)
```

### 7.2 깊이 정렬

- 그리는 순서: 바닥 → 바닥층(러그, 부지 분필선) → 나머지를 `sy`(기준점의 화면 y) 오름차순, 같으면 `sx` 오름차순 → 월드 UI(말풍선, 머리 위 표시, 진행 점) → HTML 오버레이.
- 2×2 건물은 기준점(부지 중심)의 `sy`를 쓴다. 캐릭터는 발 위치.
- 캐릭터가 건물 부지 안으로 들어가지 않게 이동 경로를 짠다 (부지 앞 칸에서 작업). 그러면 중심 기준 정렬로 충분하다.

### 7.3 에셋 컴포넌트

- `tools/extract-assets.ts`가 `design/canvas/*.dc.html`에서 `data-asset-id`가 붙은 `<svg>`를 뽑아 React 컴포넌트로 만든다 (방법은 03 문서 4장).
- 색 구멍(`{{roof}}` 등)은 CSS 변수로 바꾼다: 건물 `--roof --roof-l --roof-r --tint`, 가구 `--fab --fab-l --fab-r`. 컴포넌트를 감싸는 `<g style={{'--roof': ...}}>`에서 슬롯 색을 준다.
- 선 굵기 구멍(`{{w3}}` 등)은 `calc(var(--sw-local) * 1)` 형태로. `--sw-local = 3 / 배율`.

### 7.4 캐릭터 리그 런타임

```ts
// design/rig.json을 읽어 파츠별 transform 문자열을 만든다
function partTransform(v: [number, number, number] = [0, 0, 0], pivot: [number, number]) {
  return `translate(${v[0]} ${v[1]}) rotate(${v[2]} ${pivot[0]} ${pivot[1]})`;
}
// 프레임 = poses[pose].frames[floor(tick / rate) % frames.length]
// tick은 전역 150ms 타이머 하나. 캐릭터마다 phase를 더해 동작이 겹치지 않게
// 귀 회전 × species.earGain, 표정 = frame.expr (없으면 normal), 소품 칸 = poses[pose].prop
// 좌우 반전: 캐릭터 루트에 scale(-1 1) (오른쪽으로 걸을 때)
```

- 캐릭터 SVG의 파츠 그룹은 `data-part`로 찾는다. 원본의 `id`는 한 화면에 여러 캐릭터가 뜨면 겹치므로 코드에서는 쓰지 않는다 (03 문서 "알려진 문제").
- 애니메이션은 React 상태로 매 프레임 다시 그리지 말고, 전역 타이머가 `requestAnimationFrame`에서 `setAttribute('transform', …)`로 직접 바꾼다 (8.4).
- 바다 테마는 `rig.json` 위에 `rig.sea.json`을 덮는다. 종마다 다른 눈·볼터치·얼굴 기본 위치(`eye`, `blush`, `faceOff`)와 이동 포즈 바꾸기(`movePose`), 거품·그림자 효과가 더해진다. 런타임은 이 필드가 없으면 잔디 기본값을 쓰도록 처음부터 선택 필드로 받는다 (05 문서 6장).

### 7.5 카메라

- 월드 전체를 담은 `<g transform="translate(tx ty) scale(z)">`. 줌 0.6~1.6, 기본은 마을이 화면에 꽉 차게.
  - **전체 보기 (2026-10-01, M14):** 자동 맞춤은 **섬 전체가 늘 보이게** 한다 — 월드 바깥 여백(옆 88, 아래 24) 안만 잘라 꽉 채우고(16칸이면 예전 ×1.1과 거의 같음), 큰 섬(Lv.3부터 ring 2 이상)이면 0.6보다 작아도 된다. 손으로 줄이는 바닥은 `min(0.6, 전체 보기 배율)`, 위는 1.6 그대로. 섬이 넓어지면(레벨업·부지) 다시 맞춘다(넓어질 때 한 번). 0.75 밑이면 이름표를 숨긴다(06 문서 7장).
- 줌은 선 보정을 하지 않는다 (디자인 규칙). 에셋 자체의 배율(캐릭터 0.45 등)만 보정.

## 8. 마을 배치

### 8.1 구역

맵은 16×16 타일부터 시작해 필요하면 4칸씩 넓힌다. 가운데 4×4 광장(분수, 게시판, 벤치), 광장을 지나는 십자 길(폭 2).

**넓히기 (2026-09-30, 01 문서 D10)**: 좌표는 처음 16×16 기준 그대로 두고(광장 가운데 = (8, 8), 이미 놓인 부지는 움직이지 않음) 섬을 **사방으로 4칸씩** 키운다: `VillageState.ring` = k이면 타일 범위는 `[-4k, 16 + 4k)`, 크기 16 + 8k. 구역은 광장을 기준으로 한 사분면이라 그대로 바깥으로 커지고, 십자 길은 섬 끝까지 늘어난다. `findLot`이 구역에서 부지를 못 찾으면 프로젝터가 `ring`을 하나 올리고 다시 찾는다(결정적, 재생해도 같음). 상한 `layout.maxRing`(기본 8 = 80×80) — 넘으면 예전처럼 부지 없음 안내. 화면은 `sceneFromState`가 음수 좌표를 `off = 4k`만큼 밀어 0부터 그린다(바닥·길·광장·부지·캐릭터 모두 이 한 곳에서). 마을이 넓어지면 카메라가 새 크기로 다시 맞춘다.

**자라기 (01 문서 3.3 D8)**: 시설·집 부지는 처음부터 잡지 않고 그것이 생길 때 잡는다. `facilities`는 처음에 비어 있다(`Partial`). 광장·길 바닥과 광장 가구는 `foundedAt`이 있을 때만 그린다.

| 구역 | 위치 | 내용 |
|---|---|---|
| 북 (x<6, y<6) | 뒤쪽 | 시청 3×3 (첫 일, 광장에 가장 가까운 자리) → 외부인 시설 3채 (처음 올 때) |
| 서 (x<6, y≥10) | 왼쪽 | 팀원 집 (입주 순서대로) |
| 남 (x≥10, y≥10) | 앞쪽 | 팀원 일터 3×3 (처음 일할 때) |
| 동 (x≥10, y<6) | 오른쪽 | 남쪽이 차면 일터 |

- 부지 후보는 구역 안에서 광장에 가까운 순서로 나선형으로 도는 칸 — 집·시설 2×2, 일터 3×3(`Lot.size` 3). 길·광장·다른 부지와 겹치지 않고, 부지 사이에 1칸 이상 간격.
- 일터 건물(2×2)은 부지 왼쪽 위에 서고 앞줄·오른쪽 줄은 앞마당(일하는 자리·자재 더미), 큰 건물은 3×3 전부 — 층이 올라도 **자리를 옮기지 않는다**. 남쪽이 차면 동쪽, 그래도 모자라면 섬을 넓힌다.
- 공공시설 (M14, 06 문서 6.4): 가로등 = 길 양옆 줄(x 6·9, y 6·9)에서 광장 끝부터 2칸째·그 뒤 4칸마다, 벤치·꽃밭 = 광장 둘레 6칸, 공원·랜드마크 = 광장에 가장 가까운 빈 3×3, 두 번째 랜드마크 = 첫 랜드마크의 반대 구역. 레벨업마다 `ring + 1`(`layout.maxRing`까지). 자리는 규칙(`layout/lots.ts` `roadsideSpots`·`PLAZA_RIM`, `rules/village.ts`)이 정하고 상태에 둔다.
- 빈 칸에는 seed로 나무·덤불·꽃밭을 뿌린다. 건물이 들어오면 그 칸의 장식은 치운다.

### 8.2 캐릭터 이동

- 목적지: 작업 중 = 자기 일터 앞마당 (큰 건물이면 3×3 앞 줄), 팀장·공사 돕는 외부인은 `activeSite`(가장 최근에 일을 시작한 팀원의 일터, 06 문서 5.9), 회의 = 게시판 앞 반원, 휴식 = 자기 집 문 앞.
  - M5 리뷰: 바로 앞(화면 아래) 칸 `(x, y+1)`·`(x+1, y+1)`이 부지·가구인 자리는 앞 건물에 가려져 맨 뒤로 돌린다 → 뒷줄 집·해도실은 문 앞 대신 오른쪽 옆 칸. 물범 쉼터 바위도 가려지는 것은 건너뛴다.
- 경로: 길 칸 우선 A* (타일 격자). 속도 1.5 타일/초. 방향이 오른쪽이면 반전.
- 막힘은 가던 길도 멈추고 그 자리 (01 문서 4장 "제자리"). 첫 스냅샷의 캐릭터는 목적지에 바로 두고, 그 뒤에 나타난 외부인은 자기 시설 문 앞에서 나와 걷는다 (01 문서 3.2).
- 바위 위(발 높이 +25)에서 떠날 때는 첫걸음에 내려온다 — 환호 2초로 멈춘 동안은 바위 위 그대로.

### 8.3 성능 목표

- 캐릭터 20, 건물 40, 소품 150에서 60fps (M10에서 측정).

### 8.4 최적화 순서 (느릴 때만)

1. 바닥·길·광장은 하나의 정적 `<svg>`로 (지금 설계대로)
2. 완공 건물과 소품은 `React.memo` + 바뀔 때만 다시 그림
3. 애니메이션은 DOM 직접 조작 (7.4)
4. 그래도 느리면 정적 레이어를 `<canvas>`에 구워 두고 움직이는 것만 SVG

| PUT | `/api/projects/:id/settings` | M9 설정 화면: 본문 `{ members?: { [name]: { species, job, accessory } }, leader?: { species, job, accessory }, gameDayMs? }` → 타이쿤 저장 공간 `<DB 폴더>/settings/<마을 id>.json`(기본 `~/.subagent-tycoon/settings/`)에 합쳐 쓴다 — 사용자 프로젝트 폴더에는 쓰지 않는다(01 문서 10장·D14). 우리 파일이 없으면 프로젝트의 옛 `.claude/tycoon.json`을 읽어 시작값으로(읽기만). 동물·소품은 바다 id도 받고 정본 id로 적는다, `accessory` null = 소품 없음, 직업은 `jobPresets`·`fallbackPreset` id, `gameDayMs` 정수 60000~86400000, `members` 이름은 떠나지 않은 팀원만. 목록 밖 값도 그 팀원의 지금 값과 같으면 받는다. 200 `{ path, backup }`(backup은 원래 파일이 없었으면 null) / 본문 400 / 없는 마을·팀원 404 / 설정 파일이 깨짐 409. 쓰기가 실패하면 임시 파일을 지우고 500. 쓰고 나서 roster를 다시 읽는다 — 다시 읽기가 실패해도 파일은 바뀌었으니 200(로그만, 다음 SessionStart가 읽는다) |
| POST | `/api/projects/:id/replay` | 개발용: raw_events 재생. 도는 동안 이벤트 루프가 서서 `/hook`도 기다린다 → Claude Code가 돌 때는 쓰지 않는다 (느려지면 snapshots) |

- 사용자 행동(구매, 이름 변경, 가구 옮기기)도 raw_events에 `hook: 'ui'`로 기록 → 재생 가능.
- 쓰기(PUT·POST)는 모두 같은 규칙: Host·Origin 검사(403), 본문 1MB, 본문은 JSON(content-type은 보지 않음 — 다른 사이트는 Origin에서 막힌다).
- 게임 시계 (2026-09-30, 01 문서 6.2 활동 시간): 수집기는 `TYCOON_CLOCK_MS`(기본 10000)마다 마을을 보고, 지금 시각 < `activeUntil(state, cfg)`인 마을에만 `'clock'` 줄을 기록한다(→ `Tick`). 사용자 행동(`'ui'` 줄)은 `activeUntil`을 늘리지 않는다. 쉬는 마을엔 줄을 넣지 않는다 → 쉬는 마을은 `lastAt`이 안 바뀌어 `/`(가장 최근 마을)를 가로채지 않는다. e2e는 `TYCOON_CLOCK_MS` 250 + tycoon.json `overrides.time.gameDayMs`를 몇 초로 줄이고, 실행 하나를 열어 둔 동안 날이 간다.
